## Issue 8 — Employee ID → email lookup (most important)

### Current implementation
- `supabase/migrations/0015_resolve_employee_email.sql` defines
  `public.get_email_by_employee_code(p_employee_code TEXT) RETURNS TEXT`,
  `SECURITY DEFINER`, exact match `employee_code = p_employee_code`.
- No `REVOKE` / `GRANT` exists anywhere in the migrations, so PostgreSQL's default
  `EXECUTE … TO PUBLIC` applies → the **anon** role can call it.
- `SECURITY DEFINER` runs as the owner, so RLS on `employees` is bypassed.
- `src/pages/Login.tsx` calls it **before** sign-in with the anon key, and the browser
  receives the employee's **email address** in the response.

### Impact
Anyone with the public site (the anon key is in the JS bundle) can call
`POST /rest/v1/rpc/get_email_by_employee_code` with `EMP001`, `EMP002`, … (codes are
sequential, generated by `create-employee`) and collect every employee's email. That
enables targeted phishing and password-spraying against known accounts.

### Recommended fix
Employee ID + password → **server** resolves the code and signs in → browser receives
only a session. The email never reaches an unauthenticated browser.

1. New Edge Function `employee-id-login` (draft below), deployed with `verify_jwt = false`
   (it is a login endpoint).
2. Client: in `Login.tsx`, when the input is not an email, call
   `supabase.functions.invoke('employee-id-login', { body: { employee_code, password } })`
   and then `supabase.auth.setSession({ access_token, refresh_token })`. Email login is unchanged.
3. Then apply part 8 of the SQL (revoke anon/authenticated, case-insensitive lookup).

Order matters: deploy function → switch client → revoke. Revoking first breaks Employee-ID login.

**Rate limiting:** all Employee-ID logins would reach Supabase Auth from the Edge
Function's IP, so per-IP auth rate limits no longer protect individual users. Add a small
`login_attempts` table (code, ip, created_at) and refuse after e.g. 5 failures / 15 min per
code and per client IP (`x-forwarded-for`). Always return the same generic error and keep
the response time similar whether the code exists or not.

**Simpler alternative** (if Edge Functions are not wanted): drop Employee-ID login and
allow email login only, then revoke the function. Smallest change, but users lose a feature.

```ts
// supabase/functions/employee-id-login/index.ts  (DRAFT — not deployed)
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2';

const cors = { 'Access-Control-Allow-Origin': '*', 'Access-Control-Allow-Headers': 'authorization, x-client-info, apikey, content-type' };
const GENERIC = { error: 'Invalid email/Employee ID or password.' };

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: cors });
  if (req.method !== 'POST') return new Response('Method not allowed', { status: 405, headers: cors });

  const { employee_code, password } = await req.json().catch(() => ({}));
  if (typeof employee_code !== 'string' || typeof password !== 'string' || !employee_code.trim() || !password) {
    return Response.json(GENERIC, { status: 401, headers: cors });
  }

  const url = Deno.env.get('SUPABASE_URL')!;
  const admin = createClient(url, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!, { auth: { persistSession: false } });
  const anon  = createClient(url, Deno.env.get('SUPABASE_ANON_KEY')!,         { auth: { persistSession: false } });

  // TODO: rate-limit check (login_attempts) here.

  const { data: email } = await admin.rpc('get_email_by_employee_code', { p_employee_code: employee_code });
  // Same path / same message whether or not the code exists.
  const { data, error } = await anon.auth.signInWithPassword({
    email: typeof email === 'string' && email ? email : 'no-such-user@invalid.local',
    password,
  });
  if (error || !data.session) {
    // TODO: record failed attempt
    return Response.json(GENERIC, { status: 401, headers: cors });
  }
  // Only tokens go back; never the email.
  return Response.json(
    { access_token: data.session.access_token, refresh_token: data.session.refresh_token },
    { headers: cors },
  );
});
```

Database changes required: **yes** (REVOKE + function replace + index). Applied: **NO**.

## Issue 7 — Forced password change can be bypassed

### Current implementation
- **Stored:** `auth.users.raw_user_meta_data.force_password_change = true`, set by
  `supabase/functions/create-employee/index.ts` (`user_metadata: { …, force_password_change: true }`).
- **Checked:** only in the browser — `ProtectedRoute.tsx` and `Login.tsx` read
  `user.user_metadata.force_password_change` and redirect to `/change-password`.
- **Cleared:** `ChangePassword.tsx` calls `supabase.auth.updateUser({ password, data: { force_password_change: false } })`.

### Weakness
`user_metadata` is writable by the user. From the browser console:
`supabase.auth.updateUser({ data: { force_password_change: false } })` clears the flag
**without changing the password**. Also, the database never checks the flag, so the
REST API (anon key + the user's token) gives full normal access while the change is
"required". Risk is moderate: the person must already know the admin-issued password.

### Recommended fix
1. **Store the flag in `app_metadata`** (only `service_role` can write it):
   - `create-employee`: `app_metadata: { force_password_change: true }` (instead of user_metadata).
   - New Edge Function `complete-password-change` (requires JWT): validates the new
     password (≥ 8 chars), then
     `admin.auth.admin.updateUserById(uid, { password, app_metadata: { force_password_change: false } })`.
   - `ChangePassword.tsx` calls that function, then `supabase.auth.refreshSession()`.
   - Client checks read `user.app_metadata.force_password_change`.
2. **Enforce in the database** (SQL part 7): `password_change_pending()` reads the JWT's
   `app_metadata`; `get_auth_role()` and `get_auth_employee_id()` return NULL while it is
   true, so every RLS policy built on them denies access until the password is changed.
3. Policies that use `auth.uid()` directly are not covered — list them first (query in the SQL file).

RLS / server-side validation required: **yes, both** (Edge Function for the change, RLS helpers for enforcement).
Database changes required: **yes**. Applied: **NO**.

## Related note (not changed)
`get_auth_role()` (20260930163500) grants `ADMIN` to any JWT whose email is
`admin@gmail.com` even without a profile. Safe only while public sign-ups are disabled and
that email stays owned by the real admin. Worth removing once the admin profile is stable.
